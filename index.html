What is an API?

API stands for Application Programming Interface — it's the backbone of modern software. Almost every app you use daily relies on APIs to communicate with servers, fetch data, or connect to third-party services.

The Restaurant Analogy
🍽️
You (Client)
Sit at the table and order from the menu — you don't care how the kitchen works.
📋
API (Waiter)
Takes your order to the kitchen and delivers the response back to your table.
🔥
Server (Kitchen)
Processes the request and prepares the response — all the logic lives here.
Why APIs Matter — For Everyone
📱 Mobile Apps
Your weather app fetches live data through a weather API every time you open it.
💳 Payments
Stripe, Paystack, Flutterwave all expose APIs to process money securely.
🤖 AI
ChatGPT, Claude, Gemini — every AI product you use is accessed through an API.
🔗 Integration
Banks, logistics, hospitals — systems talk to each other through APIs 24/7.
Key insight: APIs let you build on top of existing services instead of rebuilding everything from scratch. You use the Twitter API to post tweets, not rebuild Twitter.

Concept

REST APIs

REST (Representational State Transfer) is an architectural style — a set of constraints for how web services should behave. It's not a protocol, it's a convention.

The 6 REST Constraints
1StatelessEvery request contains ALL information needed. The server stores no session between requests.
2Client-ServerFrontend and backend are completely separate — they can evolve independently.
3Uniform InterfaceResources identified by URLs. Standard HTTP methods. Consistent response format.
4CacheableResponses can be cached by clients/proxies to reduce server load and latency.
5Layered SystemClient doesn't know if it's talking to the real server, a cache, or a load balancer.
6Code on DemandOptional: server can send executable code (JavaScript) to clients.
Resources — Think Nouns, Not Verbs
❌ Bad (RPC-style):  /getUser    /createPost    /deleteComment
✅ Good (REST-style):  /users    /posts    /comments — the HTTP method tells the server what to do with the resource.
javascript — Express.js REST skeleton
const express = require('express');
const app = express();

app.use(express.json()); // Parse incoming JSON bodies

// Resource: /users — all CRUD operations on one URL pattern
app.get('/users', getAllUsers);       // Read all
app.post('/users', createUser);      // Create
app.get('/users/:id', getUser);      // Read one
app.put('/users/:id', replaceUser);   // Replace
app.patch('/users/:id', updateUser); // Partial update
app.delete('/users/:id', deleteUser); // Delete

app.listen(3000, () => console.log('API live on port 3000'));

How to Pass Data to the Backend

There are four distinct ways to send data in an HTTP request. Knowing when to use each one is fundamental to designing correct, secure APIs.

The 4 Ways to Send Data
ParamsRoute Parameters/users/:id — identifies a specific resource. Always use for resource IDs.
QueryQuery String/posts?page=2&sort=asc — filtering, sorting, searching, pagination.
BodyRequest BodyJSON payload in POST/PUT/PATCH. Used for creating or updating resources.
HeadersHTTP HeadersAuthorization tokens, API keys, Content-Type — metadata and auth, not data.
javascript — accessing all 4 data sources in Express
// Route: POST /api/v1/users/:id/posts?notify=true
app.post('/api/v1/users/:id/posts', (req, res) => {

  // 1. Route parameters → req.params
  const userId = req.params.id;      // "42"

  // 2. Query string → req.query
  const notify = req.query.notify;   // "true"

  // 3. Request body → req.body  (requires express.json())
  const { title, content, tags } = req.body;

  // 4. Headers → req.headers
  const token  = req.headers['authorization']; // "Bearer eyJ..."
  const apiKey = req.headers['x-api-key'];

  res.status(201).json({ userId, notify, title, content, tags });
});
Security rule: Never put sensitive data in query strings — they appear in server logs, browser history, and referrer headers. Auth tokens always go in headers.

HTTP Status Codes

Status codes are 3-digit numbers your API returns to tell the client exactly what happened. They're the universal language between client and server — use them precisely.

2xx — Success
200OKGeneric success. Use for GET, PUT, PATCH responses.
201CreatedResource created successfully. Always use after a successful POST.
204No ContentSuccess but nothing to return. Perfect for DELETE — no body needed.
3xx — Redirect
301Moved PermanentlyURL changed forever. Clients and search engines should update their links.
304Not ModifiedCached version is still valid — no need to resend the body.
4xx — Client Errors (their fault)
400Bad RequestMalformed JSON, missing required fields, invalid data format.
401UnauthorizedNot authenticated — missing, expired, or invalid token. Please log in.
403ForbiddenAuthenticated but lacking permission. You're logged in but this isn't yours.
404Not FoundResource doesn't exist at this URL. Check the ID.
409ConflictDuplicate entry — email already exists, username taken.
422UnprocessableValidation failed — format is valid JSON but the values break business rules.
429Too Many RequestsRate limit exceeded — slow down or upgrade your plan.
5xx — Server Errors (your fault)
500Internal Server ErrorSomething crashed on the server. This is always a bug you need to fix.
503Service UnavailableServer is down, overloaded, or in maintenance mode.
javascript — correct status code usage in Express
app.get('/users/:id', async (req, res) => {
  const user = await User.findById(req.params.id);
  if (!user) return res.status(404).json({ error: 'User not found' });
  res.status(200).json({ success: true, data: user });
});

app.post('/users', async (req, res) => {
  const user = await User.create(req.body);
  res.status(201).json({ success: true, data: user });
});

app.delete('/users/:id', async (req, res) => {
  await User.findByIdAndDelete(req.params.id);
  res.status(204).send(); // 204 = no body
});

HTTP Methods (Request Categories)

HTTP methods tell the server what action to perform on a resource. Each has a specific meaning and expected behavior — this predictability is what makes REST so powerful.

Method Reference Table
MethodCRUD ActionSafe?Idempotent?Has Body?Response
GETRead✅ Yes✅ Yes❌ No200 + data
POSTCreate❌ No❌ No✅ Yes201 + created
PUTReplace all❌ No✅ Yes✅ Yes200 + updated
PATCHUpdate partial❌ No⚠️ Sometimes✅ Yes200 + updated
DELETERemove❌ No✅ YesRare204 no body
HEADRead (headers only)✅ Yes✅ Yes❌ No200 no body
Idempotent means calling it 10 times gives the same result as 1 time. GET /users/42 always returns the same user. DELETE /users/42 deletes once — subsequent calls return 404, but the state is the same: the user is gone.
PUT vs PATCH — The Most Confused Pair
javascript
// PUT — replace the ENTIRE resource (must send all fields)
// PUT /users/42  →  body must include name, email, role, bio, etc.
{ "name": "New Name", "email": "new@email.com", "role": "admin" }

// PATCH — update ONLY the specified fields, merge with existing
// PATCH /users/42  →  only name changes, everything else stays
{ "name": "New Name" }

// Express PATCH handler:
app.patch('/users/:id', async (req, res) => {
  const user = await User.findByIdAndUpdate(
    req.params.id,
    { $set: req.body },  // merge — don't replace
    { new: true }
  );
  res.json({ success: true, data: user });
});

Client-Server Flow

Understanding the full journey of an API request — from browser click to database query and back — helps you debug problems and design better systems from day one.

Full Request Lifecycle
1. Client sends HTTP request (browser, mobile app, Postman, curl)
↓
2. DNS resolves domain → finds the server's IP address
↓
3. TCP handshake + TLS (HTTPS encryption handshake)
↓
4. Express receives request → runs middleware chain (logger, auth, validate)
↓
5. Route handler runs → queries database, executes business logic
↓
6. Response sent back with status code + JSON payload
↓
7. Client receives response → renders UI or handles the error
Making API Calls from the Frontend
javascript — fetch API (browser / Node.js)
async function createPost(postData) {
  try {
    const response = await fetch('https://api.myapp.com/posts', {
      method: 'POST',
      headers: {
        'Content-Type': 'application/json',
        'Authorization': `Bearer ${localStorage.getItem('token')}`
      },
      body: JSON.stringify(postData)
    });

    if (!response.ok) {
      const error = await response.json();
      throw new Error(error.message || `HTTP ${response.status}`);
    }

    return await response.json();
  } catch (err) {
    console.error('API Error:', err.message);
    throw err; // rethrow so the UI can handle it
  }
}

Middleware in Express

Middleware is code that runs between receiving a request and sending a response. It's the most powerful pattern in Express — the entire framework is built around it.

The Middleware Pipeline
Incoming Request
↓
Logger — logs method, URL, timestamp
↓
CORS — sets access control headers
↓
Auth — validates JWT token
↓
Validation — checks request body
↓
Route Handler — business logic + DB query
↓
Response sent to client
javascript — all middleware patterns
// 1. Global middleware (runs on every request)
app.use(express.json());   // parse JSON bodies
app.use(cors());            // allow cross-origin requests
app.use(helmet());         // set security headers

// 2. Custom logger middleware
const logger = (req, res, next) => {
  console.log(`[${new Date().toISOString()}] ${req.method} ${req.url}`);
  next(); // CRITICAL: must call next() or request hangs forever
};
app.use(logger);

// 3. Auth middleware — protect specific routes
const requireAuth = (req, res, next) => {
  const token = req.headers.authorization?.split(' ')[1];
  if (!token) return res.status(401).json({ error: 'No token' });
  try {
    req.user = jwt.verify(token, process.env.JWT_SECRET);
    next();
  } catch {
    res.status(401).json({ error: 'Invalid token' });
  }
};

// Apply to specific routes only
app.get('/profile', requireAuth, getProfile);
app.post('/posts', requireAuth, createPost);

// 4. Global error handler (MUST have 4 params, always last)
app.use((err, req, res, next) => {
  console.error(err.stack);
  res.status(err.status || 500).json({ error: err.message });
});

API Pagination

Never return all records at once — it kills performance. Pagination breaks large datasets into manageable chunks. There are three main strategies, each with real tradeoffs.

Types of Pagination
OffsetPage-based?page=2&limit=10 — Simple, predictable. Can miss/duplicate records if data changes during browsing.
CursorPointer-based?cursor=eyJpZCI6MTAwfQ — Stable, efficient. Perfect for infinite scroll feeds (Twitter, Instagram).
KeysetRange-based?after_id=100 — Fastest for sorted data. Used by most high-performance social feeds and APIs.
javascript — offset pagination (most common)
app.get('/posts', async (req, res) => {
  const page  = parseInt(req.query.page)  || 1;
  const limit = parseInt(req.query.limit) || 10;
  const skip  = (page - 1) * limit;

  const [posts, total] = await Promise.all([
    prisma.post.findMany({ skip, take: limit, orderBy: { createdAt: 'desc' } }),
    prisma.post.count()
  ]);

  res.json({
    success: true, data: posts,
    pagination: {
      page, limit, total,
      totalPages: Math.ceil(total / limit),
      hasNext: page * limit < total,
      hasPrev: page > 1
    }
  });
});
javascript — cursor pagination (infinite scroll)
app.get('/posts', async (req, res) => {
  const { cursor, limit = 10 } = req.query;

  const posts = await prisma.post.findMany({
    take: parseInt(limit) + 1,     // fetch 1 extra to check hasNext
    skip: cursor ? 1 : 0,
    cursor: cursor ? { id: parseInt(cursor) } : undefined,
    orderBy: { id: 'desc' }
  });

  const hasNext = posts.length > parseInt(limit);
  if (hasNext) posts.pop(); // remove the extra item

  res.json({
    data: posts,
    nextCursor: hasNext ? posts[posts.length - 1]?.id : null
  });
});

Auth

Authentication vs Authorization

These two words are constantly confused but mean completely different things. Mixing them up leads to serious security bugs. Get this distinction locked in.

The Core Difference
🪪
Authentication (AuthN)
"Who are you?" — Verifying identity. Login, signup, token validation, biometrics. Proves you are who you claim to be.
🛡️
Authorization (AuthZ)
"What can you do?" — Checking permissions after identity is confirmed. Roles, scopes, policies, ownership checks.
Analogy: Authentication is showing your ID at the door (proving who you are). Authorization is the bouncer checking you're on the VIP list (what you're allowed to do).
javascript — RBAC (Role-Based Access Control)
// requireAuth = authentication (who are you?)
// requireRole = authorization (what can you do?)

const requireRole = (...roles) => (req, res, next) => {
  if (!roles.includes(req.user.role)) {
    return res.status(403).json({ error: 'Forbidden: insufficient permissions' });
  }
  next();
};

// Only admins can delete users
app.delete('/users/:id', requireAuth, requireRole('admin'), deleteUser);

// Admins and moderators can ban posts
app.post('/posts/:id/ban', requireAuth, requireRole('admin', 'mod'), banPost);

// Anyone authenticated can create a post
app.post('/posts', requireAuth, createPost);

Auth

How Tokens Work

Tokens replace passwords for every request after login. They're a secure, stateless way to prove identity without sending credentials repeatedly over the wire.

javascript — login endpoint that issues tokens
app.post('/auth/login', async (req, res) => {
  const { email, password } = req.body;
  const user = await prisma.user.findUnique({ where: { email } });

  if (!user || !await bcrypt.compare(password, user.passwordHash)) {
    return res.status(401).json({ error: 'Invalid credentials' });
  }

  // Access token — short-lived (15min). Sent in every request header.
  const accessToken = jwt.sign(
    { id: user.id, email: user.email, role: user.role },
    process.env.JWT_SECRET,
    { expiresIn: '15m' }
  );

  // Refresh token — long-lived (7d). Used ONLY to get new access tokens.
  const refreshToken = jwt.sign(
    { id: user.id },
    process.env.REFRESH_SECRET,
    { expiresIn: '7d' }
  );

  // Store refresh token in httpOnly cookie (not localStorage!)
  res.cookie('refreshToken', refreshToken, {
    httpOnly: true, secure: true, sameSite: 'strict', maxAge: 7 * 24 * 60 * 60 * 1000
  });

  res.json({ accessToken, user: { id: user.id, email, role: user.role } });
});
Access vs Refresh tokens: Access tokens expire fast (15min) for security. When they expire, the client silently uses the refresh token (in an httpOnly cookie) to get a new access token — no re-login needed. If the refresh token expires, the user logs in again.
Never store tokens in localStorage — they're vulnerable to XSS attacks. Store refresh tokens in httpOnly cookies, and keep access tokens only in memory.

JWTs Deep Dive

A JWT (JSON Web Token) is a compact, URL-safe token made of three Base64-encoded parts separated by dots. It's self-contained — no database lookup needed to validate it.

JWT Structure — Three Parts
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9Header — algo + type
.
eyJpZCI6NDIsImVtYWlsIjoieXVub0BleGFtcGxlLmNvbSIsInJvbGUiOiJ1c2VyIn0Payload — your data (claims)
.
SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5cSignature — tamper proof
javascript — decoded JWT internals
// HEADER — algorithm and token type
{ "alg": "HS256", "typ": "JWT" }

// PAYLOAD — your data (claims). Standard + custom.
{
  "id": 42,
  "email": "yuno@example.com",
  "role": "admin",
  "iat": 1706000000,   // issued at (Unix timestamp)
  "exp": 1706000900    // expires at (15 min later)
}

// SIGNATURE — HMAC-SHA256(base64(header) + "." + base64(payload) + secret)
// If ANYONE tampers with the payload, the signature becomes invalid
javascript — sign and verify JWTs
const jwt = require('jsonwebtoken');
const SECRET = process.env.JWT_SECRET; // never hardcode secrets!

// Sign — create a token
const token = jwt.sign(
  { id: 42, role: 'admin' },
  SECRET,
  { expiresIn: '15m', issuer: 'myapp.com' }
);

// Verify — validate and decode
try {
  const decoded = jwt.verify(token, SECRET);
  console.log(decoded.id);    // 42
  console.log(decoded.role);  // 'admin'
} catch (err) {
  if (err.name === 'TokenExpiredError') { /* use refresh token */ }
  if (err.name === 'JsonWebTokenError') { /* invalid token */ }
}
JWT is NOT encrypted. Anyone can Base64-decode the payload and read it. The signature only proves it wasn't tampered with. Never put passwords, credit cards, or secrets in the payload.

API Keys

API keys are static tokens for machine-to-machine authentication. They're simpler than JWT but need careful implementation — rate limiting, hashing, and rotation.

API Key vs JWT — When to Use Which
FactorAPI KeyJWT
IdentifiesAn application / integrationA specific user + their claims
ExpirationManual — you rotate when neededAutomatic — built-in expiry field
Stateless?No — requires DB lookupYes — self-contained validation
Best forServer-to-server, public APIs, CI/CDUser sessions, mobile apps, SPAs
RevocationDelete from database instantlyNeeds blocklist or wait for expiry
javascript — generate, store (hashed), and validate API keys
const crypto = require('crypto');

// Generate a cryptographically secure API key
function generateApiKey() {
  return 'myapp_' + crypto.randomBytes(32).toString('hex');
  // → myapp_a3f8b2d1c4e9...  (70 chars, 256 bits of entropy)
}

// NEVER store the raw key. Store only the SHA-256 hash.
app.post('/api-keys', requireAuth, async (req, res) => {
  const rawKey    = generateApiKey();
  const hashedKey = crypto.createHash('sha256').update(rawKey).digest('hex');

  await prisma.apiKey.create({ data: {
    name: req.body.name, hash: hashedKey, userId: req.user.id
  }});

  res.status(201).json({ key: rawKey }); // show ONCE — never again
});

// Validate incoming requests with x-api-key header
const validateApiKey = async (req, res, next) => {
  const key = req.headers['x-api-key'];
  if (!key) return res.status(401).json({ error: 'API key required' });

  const hash   = crypto.createHash('sha256').update(key).digest('hex');
  const apiKey = await prisma.apiKey.findUnique({ where: { hash } });
  if (!apiKey) return res.status(401).json({ error: 'Invalid API key' });

  req.userId = apiKey.userId;
  next();
};

require('dotenv').config();
const express     = require('express');
const cors        = require('cors');
const helmet      = require('helmet');
const rateLimit   = require('express-rate-limit');
const authRoutes  = require('./routes/auth.routes');
const postRoutes  = require('./routes/posts.routes');
const errorHandler = require('./middleware/error.middleware');

const app = express();

// Security middleware
app.use(helmet());
app.use(cors({ origin: process.env.CORS_ORIGIN }));
app.use(express.json({ limit: '10kb' }));  // limit body size

// Rate limiting
const limiter = rateLimit({ windowMs: 15 * 60 * 1000, max: 100 });
app.use('/api', limiter);

// Routes
app.use('/api/v1/auth',  authRoutes);
app.use('/api/v1/posts', postRoutes);

// Health check
app.get('/health', (req, res) => res.json({ status: 'OK', ts: Date.now() }));

// 404 catch-all
app.use((req, res) => res.status(404).json({ error: 'Route not found' }));

// Error handler (always last)
app.use(errorHandler);

const PORT = process.env.PORT || 3000;
app.listen(PORT, () => console.log(`🚀 Server running on port ${PORT}`));
Pattern: Routes define paths → Controllers handle logic → Middleware handles cross-cutting concerns. Each layer has one job. This makes testing and debugging significantly easier.
